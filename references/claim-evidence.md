# 主張・根拠・見せ方を一致させる（claim-evidence map と proof object）

主張・根拠・見せ方を、carnot の型番号に対応づけて整理したもの。ブループリントを作るときと、サンプルを自己チェックするときに読む。

## 3つの層を分ける

ページを組む前に、次の3層を別々に書き出す。3層が食い違っていたら、HTML を組む前にブループリントを直す。

1. **Message**: そのページで読み手に持ち帰ってほしい判断1つ（＝タイトル）
2. **Proof**: それを支える事実・事例・数字
3. **Visual semantics**: 線・矢印・グループ・色・強調が、見る人に何を主張してしまうか

## 根拠の4区分

「ある根拠」の各項目に、次のどれかを付ける。推論を事実の顔で載せない。

- 事実: 一次資料で確認済みのもの
- 前提: ユーザーが与えた仮定
- 推論: 書き手（AI）が導いたもの。タイトルに使うときは断定を弱める（§2.11）
- 未解決: 確認が取れていないこと。「未決事項」に集める

## claim-evidence map（ページごと）

```markdown
P<n> Message: <1文>
根拠が示すこと:
- <事実・事例> → <主張のどの部分を支えるか>
根拠が示さないこと:
- <事実・事例> は <飛躍した結論> までは示さない
見せ方のガードレール:
- <根拠> と <未検証の成果> を線でつながない
```

「根拠が示さないこと」は作り手の規律のための欄で、スライドに載せる必要はない（読み手が誤読しそうなら注記にする）。主張の広さは根拠に合わせる（slide-rules §2.11）。

## 見せ方は主張である

- **線**は「支える・流れる・属する」を意味する。関係が根拠で示せるときだけ引く。
- **チェックマーク・緑**は「検証済み」を意味する。未検証の要件には中立の点・番号を使う。
- **ゲート・関門**は「通過しないと次に進めない」を意味する。通過済みとして描くのは根拠があるときだけ。
- **循環サイクル（m29）**は「自己強化する仕組み」を意味する。主張が「まだ証明されていないリスク」なら使わない。
- **2×2（m15）**は、両軸が全対象に同じ意味で当てはまるときに使う。役割の違うプレイヤー（メーカー・商社・SaaS・SIer）を並べるなら、バリューチェーン（m31）で誰がどこを押さえているかを描く。

## 観測済みと未検証を分ける

「動きは出ているが、成果はまだ検証されていない」ページでは、観測済みのシグナル（導入実績・価格・提携・リリース）と未検証の要件（定着率・ROI・品質保証・継続契約）を別の塊に置く。観測済みのシグナルが、未検証の要件を証明したように見える配置にしない。

## 事例は文で書く

読み物型のページでは、社名・製品名に一言タグを付けるだけにしない。その事例が何を示しているかを短い文で書く。

- 弱い: 「A社: 図面検索／導入済」
- 強い: 「A社: 図面検索を設計部門全体に展開し、類似図面の再利用率が上がった。検索の価値が一部署に閉じないことを示す」

## proof object の選び方（問いの種類 → 型番号）

見栄えではなく、根拠どうしの関係から選ぶ。型番号は `python scripts/new_deck.py --list` の b／m 番号。表とカードは、それ自体が証明になっているときだけ使う。

| 問いの種類 | 強い proof object（型） | 避けるもの |
|---|---|---|
| 推移・構成比・分布・相関を示す | 単一チャート＋含意 m05、積み上げ棒 m06、分布の順位棒 b17、散布図 b18、推移 b24 | 数字を表に流し込む（§5.11） |
| 何が差を生んだかを分解する | 寄与度ブリッジ m07、増減ブリッジ m08、増減の縦棒 b23 | 原因をカードで並べる |
| 選択肢を比べて推奨する | 選択肢の比較表 m10、充足度評価表 b14、意思決定ページ m35 | 同じ重さのカードを並べる |
| 問題を分解して打ち手につなぐ | イシューツリー m25、課題→原因→解決 m24、課題と打ち手の対応 m23 | 理由の箇条書き |
| 誰がどこを押さえているか | バリューチェーン m31、プロセス×観点の行列 m16 | 無理な 2×2 |
| 段階・移行・計画 | 矢羽 b05、プロセスの段階 m28、ロードマップ m33、ガント m34 | 同じ重さの矢印ボックス |
| 前提から結論を導く | 前提→帰結の2カラム b06、主張パネル＋図 b11 | 結論のない事実の羅列 |
| 全体像を示してから深掘る | 全体マップ b02、エグゼクティブサマリー m01 | 目次だけの1枚 |

proof object は補足の文字より先に目に入ること。全ラベルを読まなくても、そのページが何を証明しているか分かるのが基準。

## 一般則と slide-rules.md のルールがぶつかるとき

carnot の slide-rules.md が優先する（同ファイル冒頭の宣言どおり）。

- 一般則の「タイトル直下のサブタイトル（なぜそう言えるか）」→ 右カラムの見出しを主張文にして担わせる（§4.20）。タイトル直下の説明文は置かない（§3）。
- 一般則の「下部のまとめ帯」と「Takeaway」→ 置かない（§4.8。例外なし）。インサイトとキーメッセージはすべてタイトルに入れる（§2.10）。入りきらない説明は右カラムの見出し（§4.20）に置き、下部には置かない。

## 読み物型の密度

読み物型では、密度も仕様の一部として扱う。文字を減らして見た目を整えた結果、話し手なしで論旨が追えなくなったら、それは失敗として扱う。根拠の骨格（数字・事例の文・出典）は残したまま、罫線・重複ラベル・装飾の囲みを削って読みやすくする。
