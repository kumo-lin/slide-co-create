# サンプルと完成版の自己チェック（Gate C の前・納品前）

サンプルの差し戻し基準と診断の順序。HTML で組むスライドに当てはまるものを、carnot の目視項目（slide-rules §8）と合わせている。

PNG（`render_pdf.py` の出力）を Read で1枚ずつ画像として見て判定する。ユーザーに見せる前に、ここで差し戻す。

## 差し戻す症状

| 名前 | 見えている症状 | 直し方 |
|---|---|---|
| 結論が複数 | タイトル・大きな数字・右カラム・注記がそれぞれ結論に見える | 結論はタイトル1つ。他は根拠か注記に格下げ |
| 下部のまとめ | スライド下部に、結論・示唆の帯・ボックス・「だから」「まとめ」で始まる行がある | 示唆をタイトルに移し、帯を消す。空いた余白は内容を足すか中央揃えで受ける（§4.12・§5.13） |
| 浮いた数字 | 大きな数字が proof object の外にあり、タイトルと競う | 数字を図の中か直近に置くか、小さくする |
| 弱い proof object | ラベル・カード・箱ばかりで、何が証明なのかが最初に見えない | claim-evidence.md の対応表から型を選び直す |
| 汎用カード並べ | 同じ重さのカードや KPI タイルが並ぶだけ | 軸のある表（b09）か、関係を描く型に変える |
| 主役の取り違え | 一番目立つ図が、副次的な論点しか証明していない | 図の大きさ・型を主張に合わせる |
| 線の過多 | 枠・罫線・薄い塗りで全部が同じ重さに見える | 枠を外し、余白と細い区切りにする。塗りは結論か仕組みだけ |
| 根拠の取り違え | 事例・数字が、示していない主張に線や配置でつながっている | claim-evidence map を直し、観測済みと未検証を分ける |
| 見せかけの精度 | 2×2 や軸図に、軸が当てはまらない対象が置かれている | バリューチェーン（m31）など役割の図に変える |
| ラベルだけの事例 | 社名＋一言タグで、何を示す事例か読めない | 事例を短い文にする |
| 詰め込み | 主張・注記・根拠が多すぎて読む順番がない | ページを分けるか、補足を付録へ |
| 読み物型でスカスカ | 見た目は整っているが、話し手なしでは論旨が追えない | 根拠の文・数字・出典を戻す |
| 文字が読めない | 本文が小さい・薄い | 文字量を減らし、タイトル・図のラベル・主要な数字を優先 |
| 図の崩れ | 棒が潰れる、図が空、下半分が空く、泣き別れ、左右カラムの下端が不揃い | パーツの CSS をデッキ側で直す（slide-rules §8） |

## 迷ったときの診断順

1. proof object が補足の数字より先に見えるか
2. 各事例・数字は、図が示唆している主張を本当に支えているか
3. 事例は前提知識なしで読めるか
4. タイトル・右カラム見出し・数字・注記がそれぞれ別の役割をしているか
5. 結論に見える場所が複数ないか
6. 本物の数字が、うっかり見出しになっていないか
7. 読み物型なら、話し手なしで論旨が追えるか
8. 色と線が階層を作っているか、全部を同じ重さにしているか
9. タイトルの大きさ・キッカー・出典行の位置がページ間でそろっているか
10. 必要な言葉と数字が読める大きさか

## 直すときは中身を変える

見た目の形容ではなく、ブループリントか proof object を変える指示にする。

- 弱い: 「もっとすっきり、プロっぽく」
- 強い: 「proof object は寄与度ブリッジ（m07）だけにする。27% と 91% は右カラムの根拠に移し、大きな数字のタイルはやめる」

**完了条件**: 表のどの症状にも当てはまらないと、ページごとに言える。
